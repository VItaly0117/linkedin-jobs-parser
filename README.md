# Парсер вакансий LinkedIn

Python + Django + PostgreSQL. Собирает вакансии по паре «поисковый запрос + страна» через гостевые (не требующие входа) запросы LinkedIn, найденные в DevTools → Network.

Парсер состоит из двух независимых частей, которые общаются только через базу:

| Часть | Команда | Что делает |
|---|---|---|
| Search | `python manage.py run_search` | Листает выдачу, сохраняет карточки вакансий и заготовки компаний |
| Details | `python manage.py run_details` | Берёт вакансии и компании из БД, собирает полные данные, обновляет записи |

## Запуск

Нужен Docker с Compose.

```bash
cp .env.example .env
docker compose up -d --build db web
```

Админка: http://localhost:8000/admin (логин и пароль — `DJANGO_SUPERUSER_*` из `.env`).

1. В разделе «Поисковые запросы» добавить запросы, например `Python Developer` / `United States`. Запросов может быть сколько угодно, с разными странами.
2. Запустить сбор — части можно запускать в любом порядке, по отдельности и одновременно:

```bash
docker compose run --rm search
docker compose run --rm details
```

3. Выгрузить результат:

```bash
docker compose run --rm web python manage.py export_jobs --format xlsx
docker compose run --rm web python manage.py export_jobs --format csv
```

Файлы появятся в `exports/`. Выгрузить выбранные вакансии можно и из админки (действие «Выгрузить выбранное в CSV»).

### Без Docker

```bash
python -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env        # в DATABASE_URL заменить хост db на localhost
.venv/bin/python manage.py migrate
.venv/bin/python manage.py createsuperuser
.venv/bin/python manage.py runserver
```

### Параметры команд

`run_search`
- `--query-id N` — только указанные запросы (можно повторять);
- `--refresh` — сбросить чекпоинты и пройти выдачу заново (собранные вакансии не удаляются);
- `--max-pages N` — не больше N страниц на срез, для быстрой проверки.

`run_details`
- `--workers N` — потоков на загрузку (по умолчанию 4);
- `--batch N` — размер пачки из очереди (20);
- `--limit N` — обработать не больше N записей;
- `--retry-failed` — повторить записи со статусом «Ошибка»;
- `--jobs-only`, `--companies-only` — только вакансии или только компании.

Настройки частоты запросов, числа повторов и прокси — в `.env` (см. `.env.example`).

## Используемые запросы LinkedIn

| Назначение | Запрос |
|---|---|
| Поиск | `GET /jobs-guest/jobs/api/seeMoreJobPostings/search?keywords=…&location=…&start=N` + `geoId`, `f_TPR` |
| Регионы страны | `GET /jobs-guest/api/typeaheadHits?query=<страна>&typeaheadType=GEO&geoTypes=…` (подсказки поля Location) |
| Вакансия | `GET /jobs-guest/jobs/api/jobPosting/<job_id>` |
| Компания | `GET /company/<slug>` (публичная страница: блок About и JSON-LD) |

Первые три — XHR-запросы, которые страница `linkedin.com/jobs/search` делает при прокрутке списка и при выборе вакансии. Ответы — HTML-фрагменты; поиск отдаёт по 10 карточек на страницу.

## Как это устроено

```
config/                    настройки Django
jobs/models.py             SearchQuery, SearchSlice, Job, Company, JobSearchHit
jobs/linkedin/client.py    HTTP: лимит частоты, повторы с backoff, прокси
jobs/linkedin/search.py    параметры поиска, разбор карточек, регионы и окна времени
jobs/linkedin/details.py   разбор страницы вакансии
jobs/linkedin/company.py   разбор страницы компании
jobs/services/             search_runner.py (часть 1), details_runner.py (часть 2)
jobs/export.py             CSV / XLSX
jobs/admin.py              админка
```

**Обход лимита выдачи.** Гостевой поиск отдаёт не больше ~1000 результатов на набор параметров. Проверка на живых запросах показала, что гостевой эндпоинт учитывает только локацию и период публикации (`f_TPR`, окно в секундах), а фильтры уровня, типа занятости, формата работы и сортировку игнорирует. Поэтому запрос представлен деревом срезов (`SearchSlice`):

1. сначала выкачивается срез «вся страна»;
2. если он упёрся в лимит, создаются срезы по регионам и крупным городам страны (берутся из подсказок локаций LinkedIn) и срез с окном «последний месяц»;
3. любой срез, упёршийся в лимит, получает дочерний срез с более узким окном: месяц → неделя → 3 дня → сутки → 12 ч → 3 ч → 1 ч.

Окна вложены друг в друга, поэтому более узкое создаётся только тогда, когда более широкое не поместилось в лимит. Пересечения между срезами безвредны — их гасит дедупликация.

**Дедупликация.** `Job.linkedin_job_id` и `Company.linkedin_slug` уникальны на уровне БД, вставка идёт через `bulk_create(ignore_conflicts=True)`. Одна вакансия, найденная по нескольким запросам или срезам, хранится один раз; связь с запросами — в `JobSearchHit` (уникальная пара «вакансия — запрос»). Страница компании запрашивается один раз на компанию, а не на вакансию.

**Повторный запуск.**
- Search сохраняет `next_start` среза после каждой страницы и при перезапуске продолжает с него.
- Details берёт записи пачками через `SELECT … FOR UPDATE SKIP LOCKED` и помечает их «В работе». Можно запускать несколько процессов одновременно. Записи, оставшиеся «В работе» после падения процесса, через 15 минут возвращаются в очередь.

**Ошибки.**
- 429, 999, 5xx, таймауты и редирект на authwall — повтор с экспоненциальной паузой (учитывается `Retry-After`), со сбросом сессии и сменой прокси.
- 404 на вакансии — статус «Удалена на LinkedIn»; 404 на компании — «Не найдена».
- Если попытки исчерпаны или разметка неожиданная — статус «Ошибка», текст в `last_error`, счётчик попыток растёт; процесс продолжает работу. После 5 попыток запись больше не берётся автоматически; вернуть её в очередь можно действием в админке.
- Страницы компаний запрашиваются без cookie: с cookie от предыдущих запросов LinkedIn отвечает на них кодом 999.

## Собираемые данные

**Вакансия:** ID, название, ссылка, локация, дата публикации, уровень, тип занятости, функция, отрасли, зарплата (если указана), число откликов, внешняя ссылка для отклика, признак Easy Apply, признак закрытия, описание (текст и HTML), поисковые запросы, по которым найдена.

**Компания:** slug и ID LinkedIn, название, ссылка, сайт, отрасль, размер, число сотрудников в LinkedIn, штаб-квартира, тип, год основания, специализации, число подписчиков, слоган, описание, логотип, JSON-LD (адрес и пр.).

## Результаты тестового прогона

Запрос `Python Developer` / `United States`, один IP без прокси, 16.11.2026.

| | Количество |
|---|---|
| Вакансий найдено (Search) | 10 865 |
| Дублей по `linkedin_job_id` | 0 |
| Вакансий с полными деталями (Details) | 10 865 (100 %) |
| Вакансий с ошибкой после повторов | 0 |
| Компаний найдено | 3 056 |
| Компаний с собранными данными | 3 056 (100 %) |
| Вакансий без страницы компании на LinkedIn | 179 |
| Срезов поиска пройдено | 14 из 32 |

- Поиск остановлен вручную после 10 тыс. вакансий: срез «вся страна» дал 1000, затем срезы по штатам давали по 600–970 новых каждый. Оставшиеся 18 срезов и запросы по другим странам продолжатся с чекпоинтов при следующем запуске `run_search`.
- Скорость Details с одного IP — 45–90 вакансий в минуту (ограничивается ответами 429); три вакансии исчерпали 6 попыток и были собраны повторным запуском с `--retry-failed`.
- Процессы несколько раз останавливались и запускались заново — дублей и потерянных записей не появилось.

Выгрузка: `exports/jobs.csv` и `exports/jobs.xlsx` — одна строка на вакансию, 38 колонок, поля компании с префиксом `company_`.

## Ограничения

- Гостевые страницы не содержат часть данных, доступных после входа (например, точное число откликов, навыки, контакт рекрутёра).
- Формат работы (On-site / Remote / Hybrid) гостю недоступен: фильтр `f_WT` игнорируется, а на странице вакансии этого поля нет.
- «Все доступные вакансии» ограничены тем, что LinkedIn показывает гостю: если регион за самый узкий период всё ещё даёт больше 1000 результатов, остаток недостижим.
- Скорость ограничена частотой запросов с одного IP; для ускорения — список прокси в `LINKEDIN_PROXIES`.
- Автоматический сбор данных не разрешён пользовательским соглашением LinkedIn. Используются только публичные страницы, без учётной записи и с умеренной частотой запросов.
